Each provider decides how its credential is supplied and what a connection to it can be used for. The capabilities below are what each provider can serve; you choose which of them a given connection holds when you connect it.

## Cloud and infrastructure

| Provider | Credential | Can be used for |
|---|---|---|
| **AWS** | Assume Role with a role ARN and external ID (recommended), or an access key pair. A default region comes with it, and a workflow step can override it. | Workflows, AI |
| **Azure** | A service principal: directory (tenant) id, application (client) id, client secret, and a default subscription id. | Workflows |

Both allow more than one connection, so a production account and a staging account are two rows.

The IAM policy or Azure role assignment on the credential decides what a step can do with it. There's no second permission list inside KloudMate, so narrow the role itself and gate risky steps with an [approval](/workflows/approvals-and-input/).

:::note
This is not the same as the AWS account you connect for inventory and metrics. That one lives under [Settings → Data Sources](/platform/settings/data-sources/) and doesn't appear in the Connections list. Connect AWS here when a workflow step needs to call an AWS API, or when the AI assistant needs AWS as a tool.
:::

## Chat and issue tracking

| Provider | Credential | Can be used for |
|---|---|---|
| **Slack** | OAuth install. | Notifications, Triggers, Workflows |
| **Jira Cloud** | OAuth through Atlassian. | Notifications, Triggers, Workflows |

One Slack install serves alert notifications, incident ChatOps, the [Slack workflow actions](/workflows/actions/#slack), approval buttons, and Slack event triggers. A connection made for notifications needs reconnecting before it can receive events.

One Jira credential can reach several Atlassian sites, which is why every Jira action and trigger starts with a site picker.

## Tools and custom endpoints

| Provider | Credential | Can be used for |
|---|---|---|
| **Custom MCP Server** | A server URL, a transport of Streamable HTTP or SSE, and either no auth, a bearer token, or an API key in a header you name. Extra headers can be sent alongside, for a server that wants a routing header as well as a credential. | Workflows |
| **OAuth 2.0** | Your own authorize and token URLs, scopes, client id, and client secret, with either the client-credentials or the authorization-code grant. | Workflows |

Use **OAuth 2.0** to give an [HTTP Request](/workflows/actions/#http-request) step a credential that's refreshed for you and never stored in the workflow definition.

## AI assistant tools

These connect an MCP server the [KloudMate Assistant](/kloudmate-assistant/) can call as a tool. All of them serve the **AI** capability only, which is also the only capability that permits a [private connection](../connect-an-account/#visibility).

| Provider | Credential |
|---|---|
| **GitHub** | A GitHub token. |
| **Atlassian** | An Atlassian API token. |
| **Sentry** | OAuth. |
| **Google Cloud BigQuery** | Google OAuth. |
| **Google Cloud Compute Engine** | Google OAuth. |
| **Google Cloud GKE** | Google OAuth. |
| **Google Cloud Logging** | Google OAuth. |
| **Google Cloud Monitoring** | Google OAuth. |
| **Google Cloud Resource Manager** | Google OAuth. |

AWS also serves the AI capability, using an access key pair. See the cloud table above.

## What your plan includes

Which providers you can connect is part of your plan. The **Connect** picker is filtered to what your organization is entitled to and what the platform currently offers, so it never leads you into a refusal. A provider you expect but can't see is either not included in your plan or not currently offered, and only the first can be fixed by upgrading.

A provider can also be offered for some uses and not others. If it appears in the picker but you can't grant it the capability you wanted, that capability isn't currently offered for it.

Turning off a provider, or one of its uses, affects new connections only. Anything already connected keeps working, so existing workflows, dashboards, and notification channels don't break.

## Link your Slack account for ChatOps

One more Slack step is per person rather than per workspace. After someone with the **Developer** role connects Slack and adds a Chat Ops channel, each responder links their own Slack account before they can acknowledge or resolve incidents from Slack.

Open **Incidents → Chat Ops**, scroll to **User Settings**, and click **Connect account**. It's a one-time flow that ties your KloudMate identity to your Slack user.

Everyone links their own account, because KloudMate has to match the Slack user who pressed a button to a workspace member before it acts. The same applies to workflow [approval buttons](/workflows/approvals-and-input/#how-a-request-reaches-people).

See [Slack Integration](/incident-management/slack-integration/) for the full setup.
