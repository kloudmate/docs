Reliability isn't only a top-level area. KloudMate surfaces SLO context where you're already working — on the service detail page, on incident detail, and on alert detail.

## Service detail — Reliability tab

Every IM service detail page (`/<workspaceId>/im/services/<id>`) now has tabs:

- **Overview** (default) — the existing stat cards and integrations table.
- **Reliability** (new) — a service-scoped Create SLO button and a table of every SLO anchored on this service. Same row shape as the workspace [SLO list](./slo-detail/). Empty state with explanatory copy when the service has no SLOs yet.

Tab is URL-synced — `?tab=overview` or `?tab=reliability`. Refreshing or sharing the link preserves the active tab.

### SLO summary chip in the service header

When the service has at least one SLO, a small chip appears in the page header next to the existing labels:

- `N SLOs · Y% min compliance` — healthy.
- `N SLOs · M breached` — red, when at least one is breached.

Clicking the chip jumps to the Reliability tab. The chip is **only rendered when SLOs exist** — services without any keep the header clean.

## Incident detail — Linked SLOs panel

On incident detail (`/<workspaceId>/im/incidents/<id>`), a **Linked SLOs** panel appears below the standard service / integration / escalation-policy labels — but only when the affected service has at least one **incident-based-availability** SLO.

:::note[Placeholder image]
Screenshot pending — incident detail page with the Linked SLOs panel populated, showing two SLO cards with breach chips.
:::
![Incident detail Linked SLOs panel](../_placeholders/screenshot-placeholder.png)

Each linked SLO shows as a card:

- SLO name with **Breached** / **Disabled** chips as applicable.
- Kind + target + window.
- Current compliance %.

Clicking a card opens the SLO detail page.

Matching is **service-only** in v1 — every incident-based SLO on the affected service appears, even if the SLO's severity / metadata filters might exclude this specific incident. Slight over-reporting is the deliberate trade-off; re-implementing the SLO evaluator in the browser would be fragile.

## Alert detail — Define an SLO

The alert detail page header now includes a **Define an SLO** outlined button (admin-only) next to the existing actions (Ask AI, Jira integration, Edit Alert). Clicking it opens the SLO create wizard at `/<workspaceId>/slos/create`.

:::note[Placeholder image]
Screenshot pending — alert detail page header showing the Define an SLO CTA next to Edit Alert and Ask AI.
:::
![Alert detail Define an SLO CTA](../_placeholders/screenshot-placeholder.png)

The CTA is a discovery signal — *"this alert exists; consider an SLO covering the same condition."* It does **not** auto-prefill the wizard because alert configurations don't map cleanly to SLI / target / window choices.
