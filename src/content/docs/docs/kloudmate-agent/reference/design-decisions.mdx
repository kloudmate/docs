This page summarizes the load-bearing design decisions behind the agent and what each one means for you. They explain why the agent behaves the way it does.

## Opt-in, per-service instrumentation

Rather than instrumenting every process on a host at once, the agent instruments one service at a time, when you choose to. So a problem with one service's instrumentation never affects the others. The eBPF baseline still gives you broad coverage as soon as the agent is installed, so you get value without a system-wide change. See [Application APM overview](../../auto-instrumentation/overview/).

## Reuse the OpenTelemetry ecosystem

The agent uses the standard OpenTelemetry (OTel) language agents for Java, Node.js, Python, and .NET, activated through the standard injection environment for each runtime. It does not use a custom loader. The language agents ship inside the KloudMate agent package, versioned with it, so they upgrade together and need no separate download. See [Linux (systemd)](../../auto-instrumentation/linux-systemd/).

## Generated configuration, not a hand-edited blob

Configuration is generated from a structured set of features and integrations rather than hand-edited YAML. This is what makes it safe to turn a feature on or off from the interface, and it avoids restarting the collector when nothing really changed. The raw YAML editor remains available for advanced setups. See the [configuration model](../../concepts/config-model/).

## PHP through a version-gated tracer

PHP 7 has no native OpenTelemetry path, so the agent uses a dd-trace based tracer for PHP 7 and 8.0 to 8.1 (converted to clean OpenTelemetry) and native OpenTelemetry for PHP 8.2 and newer. One mechanism covers both modern and legacy PHP, and the traces join the same distributed traces as everything else. See [PHP instrumentation](../../auto-instrumentation/php/).

## eBPF on by default, gated by capability

The eBPF baseline is enabled by default rather than opt-in, because it gives you broad visibility with no configuration. It is gated by the host's kernel and privileges, and degrades gracefully where it is not supported, so the host still gets metrics and logs. See [eBPF observability](../../ebpf-observability/).

## One protocol for every mode

The agent and KloudMate use a single check-in protocol across virtual machines and Kubernetes, with platform-specific fields optional within it. New fields are additive, so older agents keep working. For you this is transparent: it is what lets the same discover, instrument, and report model work everywhere. See [Architecture](../../concepts/architecture/).
