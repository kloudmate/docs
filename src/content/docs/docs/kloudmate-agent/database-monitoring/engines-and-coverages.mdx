The agent monitors databases through bundled **profiles**. Each profile provides one **coverage** for one engine, and you combine coverages to get the depth you want. This page lists the engines and the coverages available for each.

## Coverage types

Coverages fall into a few types, depending on what they collect and how:

- **Standard metrics:** the engine's native health and capacity metrics (connections, cache hit ratio, replication lag, buffers, table and index statistics). Collected by the engine's native receiver. A `basic` level uses the receiver defaults; a `full` level turns on every additional metric.
- **Query performance and top queries:** aggregated statistics for the most expensive queries across all clients, read from the engine's own views (for example, `pg_stat_statements` on PostgreSQL, dynamic management views on SQL Server, and `v$` views on Oracle).
- **Locks:** lock and blocking information.
- **Query logs:** rows from diagnostic views emitted as log records.
- **Server logs, stderr logs, and slow logs:** the database's own log files.

## Connection-based and file-based coverages

There are two ways a coverage collects data, and the difference matters on Kubernetes:

- **Connection-based coverages** connect to the database (standard metrics, query performance, locks, and query logs). They need credentials but no access to the host.
- **File-based coverages** read the database's log files on the host (server logs, stderr logs, and slow logs). They need no database connection but do need access to the log files.

File-based coverages require the agent to run where the log files are, so they are available on a virtual machine but hidden on Kubernetes, where the collector scrapes databases remotely and cannot read another pod's files. See [Database monitoring on Kubernetes](../on-kubernetes/).

## Setup steps per coverage

Some coverages need a one-time setup step on the database, which the wizard shows you when you select the coverage. For example:

- PostgreSQL query performance needs the `pg_stat_statements` extension, which requires adding it to `shared_preload_libraries` and creating the extension. This step needs a PostgreSQL restart.
- Query and query-log coverages need the monitoring user to have the right grants (for example, `GRANT pg_monitor` on PostgreSQL, or the equivalent view permissions on SQL Server and Oracle).
- File-based log coverages may need a log setting enabled on the database (for example, MySQL's slow query log).

If a prerequisite is missing, the coverage reports it rather than failing silently, and the rest of the coverages keep working.

## Filtering database logs by coverage

All database log records the agent produces are tagged with a `km.db.coverage` attribute set to the coverage name (for example, `query-performance`, `server-logs`, `stderr-logs`, `slow-log`, or `query-log`). You can filter database logs by this attribute in Log Explorer to focus on one kind of coverage.
