Server-side database monitoring needs a monitoring user's credentials to connect to the engine. The agent supports three ways to provide them, so you can keep secrets out of your configuration. The wire-side eBPF view needs no credentials at all. For the general flow, see the [Database monitoring overview](../overview/).

## The three credential modes

### Environment reference (default)

The credential is stored as a reference, not a value. The generated configuration contains a placeholder such as `${env:KM_SECRET_<name>}`, and the agent resolves it from an environment variable at runtime. The plaintext value never lands in the configuration, the pushed configuration, or the collector's config file. This is the default and the recommended mode.

The agent also handles escaping for you, so a password with special characters works in a connection string without you having to encode it.

### Plaintext inline

You can enter the value directly, in which case it is written into the generated configuration. The interface shows a clear "stored unencrypted" warning, because the value then lives in the configuration and on disk. Use this only when you accept that trade-off.

### Operator-managed

The credential is still an environment reference, but you supply the environment variable yourself rather than through the wizard. This suits secrets that come from an external secret manager. How you supply the variable depends on the platform:

- **On a virtual machine:** set `KM_SECRET_<name>` for the agent, for example through the systemd `EnvironmentFile`.
- **On Kubernetes:** put `KM_SECRET_<name>` in a Kubernetes Secret and point the Helm release at it with the `dbMonitoring.secretName` value. See [Database monitoring on Kubernetes](../on-kubernetes/).

## Why environment reference is the default

Keeping the secret out of the configuration has two benefits:

- **The value stays local.** It never travels to KloudMate or into stored configuration, so your database password is not exposed through the control plane.
- **Rotation is easy.** Because the configuration holds only a reference, you rotate a password by updating the environment variable or Secret, without changing the agent's configuration.

:::note
On Kubernetes, the collector reads the Secret when its pod starts, so a rotated password takes effect on the next pod restart. See the ordering note in [Database monitoring on Kubernetes](../on-kubernetes/).
:::

## Grants

Whichever mode you use, the monitoring user needs read access to the engine's statistics and, for some coverages, specific grants (for example, `GRANT pg_monitor` on PostgreSQL). The wizard shows the exact setup steps for the coverages you selected. See [Engines and coverages](../engines-and-coverages/).
