The KloudMate agent organizes what it collects into six layers, labeled L0 through L5. The lower layers are automatic and carry no risk to your applications. The upper layers require a process restart, so you turn them on for each service when you are ready. This lets you get value right away and add deeper tracing at your own pace.

## The layers at a glance

| Layer | What it provides | How it turns on |
|---|---|---|
| L0: Discovery | Live inventory of services, runtimes, and databases | Automatic |
| L1: Host metrics and logs | CPU, memory, disk, network, and system logs | Automatic |
| L2: eBPF baseline | RED metrics, service map, Database Activity Monitoring, context propagation | Automatic (kernel-gated) |
| L3: Application APM | Distributed traces for Java, Node.js, Python, .NET | Opt-in per service |
| L4: Databases | Database metrics, query performance, and logs | Opt-in per database |
| L5: Legacy application traces | Route-level traces for PHP 7 | Opt-in per service |

## The automatic baseline (L0 to L2)

The first three layers turn on without any configuration and without touching your applications.

### L0: Discovery

Discovery inventories the application services, runtimes, and databases running on each host or cluster. It records each service's runtime (Java, .NET, Node.js, Python, PHP, Go, and Ruby), how it is managed, and which ports it listens on, and it marks whether the agent has a way to instrument it. This inventory powers the "we found these services, instrument them?" prompts in the web interface. See [Discovery](../discovery/).

### L1: Host metrics and logs

After install, the agent collects host metrics (CPU, memory, disk, and network) and system logs automatically. It needs no configuration. See [Host metrics and logs](../../baseline/host-metrics-and-logs/).

### L2: eBPF baseline

Where the Linux kernel supports it, the extended Berkeley Packet Filter (eBPF) baseline turns on by default. It watches traffic in the kernel to produce:

- **RED metrics** (Rate, Errors, and Duration) for your services.
- A **network service map** with service-to-service latency.
- **Database Activity Monitoring (DAM)**, which shows the database queries your applications run, with no credentials.
- **Trace-context propagation** across services, and links between logs and traces.

None of this needs code changes or SDKs. See [eBPF observability](../../ebpf-observability/).

## Opt-in depth (L3 to L5)

The upper layers attach to individual services and need a restart of that service, so you enable them one at a time.

### L3: Application APM

Application performance monitoring (APM) attaches tracing to an application to produce full distributed traces. You turn on a service to instrument it, agree to the restart, and traces begin flowing, joined with the eBPF spans from L2. Supported runtimes include Java, Node.js, Python, and .NET. See [Application APM](../../auto-instrumentation/overview/).

### L4: Databases

Database monitoring reads the database's own health metrics and logs, such as connections, cache hit ratio, replication lag, and slow queries. This works with the eBPF view at L2: eBPF shows the queries your applications run, while database monitoring shows the database's own health. See [Database monitoring](../../database-monitoring/overview/).

### L5: Legacy application traces

PHP 7 has no native tracing path, so the agent brings route-level tracing to PHP 7 applications through a dedicated tracer. The resulting traces join the same distributed traces as everything else. See [PHP instrumentation](../../auto-instrumentation/php/).

## Why the layers are split

The automatic layers give you safe visibility as soon as the agent is installed. The opt-in layers need a restart, so you enable them one service at a time: turn one on, check the result, then do more. You are never forced to instrument everything at once.
