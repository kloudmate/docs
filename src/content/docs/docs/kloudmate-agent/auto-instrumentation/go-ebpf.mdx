Go is the one runtime the agent does not inject. Go compiles to a static binary with no runtime to attach an agent to, so instead of code injection the agent covers Go services through the extended Berkeley Packet Filter (eBPF) baseline. There is no **Instrument** toggle to turn on for a Go service: it is covered automatically wherever the eBPF baseline is active. This applies on **Linux, Kubernetes, and Docker**, and not on **Windows**, which has no eBPF.

## Rich eBPF coverage for Go

Go gets more from eBPF than other runtimes do. The agent's eBPF tracer follows Go programs closely enough to produce distributed context across many protocols:

- HTTP
- gRPC
- Kafka
- Redis
- SQL
- MongoDB

The result is close to what a language SDK would produce, without changing your code or your build.

## How Go traces connect to other services

Because the eBPF baseline and the language agents both propagate W3C trace context (`traceparent`), a Go service joins the same distributed traces as its instrumented neighbors. When an instrumented service calls a Go service, the Go service's eBPF server span adopts the caller's trace, so you see one connected trace with a correct parent-child relationship, rather than two disjoint views. In practice, an instrumented upstream and an eBPF-only Go downstream consistently land on a single trace.

:::note
In the Discovered Services list, a Go service is marked as covered by eBPF rather than as instrumentable, and its Instrument toggle is disabled. This is expected: the eBPF baseline is already tracing it.
:::
