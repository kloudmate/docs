Go is the one runtime the agent does not inject. Go compiles to a static binary with no runtime to attach an agent to, so instead of code injection the agent covers Go services through the extended Berkeley Packet Filter (eBPF) monitoring. There is no **Instrument** toggle to turn on for a Go service: it is covered automatically wherever eBPF monitoring is active. This applies on **Linux, Kubernetes, and Docker**, and not on **Windows**, which has no eBPF.

## Rich eBPF coverage for Go

Go gets more from eBPF than other runtimes do. The agent's eBPF tracer follows Go programs closely enough to produce distributed context across many protocols:

- HTTP
- gRPC
- Kafka
- Redis
- SQL
- MongoDB

The result is close to what a language SDK would produce, without changing your code or your build.

## How Go traces connect to other services

eBPF monitoring and the language agents both propagate W3C trace context (`traceparent`). So when an instrumented service calls a Go service, the Go service's eBPF span adopts the caller's trace, and you see one connected trace with the correct parent-child relationship rather than two disjoint views.

:::note
In the Discovered Services list, a Go service is marked as covered by eBPF rather than as instrumentable, and its Instrument toggle is disabled. This is expected: eBPF monitoring is already tracing it.
:::
