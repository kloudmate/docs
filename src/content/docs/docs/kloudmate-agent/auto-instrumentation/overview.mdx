Application performance monitoring (APM) is the opt-in half of the agent. Where the eBPF baseline gives you Rate, Errors, and Duration (RED) metrics and a service map automatically, application APM attaches OpenTelemetry (OTel) auto-instrumentation to a service to produce full distributed traces, with spans for your frameworks, database calls, and outbound requests. Because it requires a process restart, you enable it one service at a time.

## The per-service opt-in flow

The flow is the same across every deployment mode:

1. **Discover.** The agent inventories your services and lists them under **Discovered Services**. See [Discovery](../../concepts/discovery/).
2. **Toggle Instrument.** You turn on the **Instrument** toggle for a service.
3. **Consent to the restart.** Instrumentation only takes effect when the process restarts, so the agent asks before restarting. You can restart now, or leave the change pending until the next restart.
4. **Traces flow.** After the restart, the service emits application traces to the agent's local collector, correlated with its eBPF spans.

Throughout this flow, the eBPF baseline keeps covering the service, so there is no visibility gap while you enable APM.

## Status chips

Each service in the list shows a status chip so you always know where it stands:

- **Instrumented:** instrumentation is applied and the service restarted cleanly.
- **Pending restart:** the change is written but the service has not restarted yet.
- **Failed, rolled back:** the restart failed, so the agent reverted the change (see rollback below).

## Restart consent and health gating

The agent never restarts your services silently. In this version:

- Every restart requires **explicit, per-service confirmation**. There is no batched or automatic restart.
- The agent restarts **one service at a time**.
- It can apply an optional **health gate**. After the restart, the agent waits for the service to become active. Where the listen port is known, it also waits for the service to accept connections before reporting success.

## Automatic rollback

If an instrumented service fails to restart or falls into a crash loop, the agent **rolls back automatically**: it removes the change, reloads, and restarts the service, returning it to its previous state, and reports the status as failed, rolled back. The eBPF baseline keeps covering it, and because you instrument one service at a time, a problem with one service never affects the others.

## Supported runtimes

| Runtime | How the agent instruments it |
|---|---|
| Java | OpenTelemetry Java agent, attached per service |
| Node.js | OpenTelemetry Node.js instrumentation, attached per service |
| Python | OpenTelemetry Python instrumentation, attached per service |
| .NET | OpenTelemetry .NET auto-instrumentation (CLR profiler) |
| PHP | Attached per service, covering both PHP 7 and PHP 8 |
| Go | Covered by the eBPF baseline, not injected |

The language agents ship inside the KloudMate agent package and are versioned with it, so there is no separate download to manage.

## Clean traces without duplicates

When you instrument a service, the agent tells the eBPF baseline to stop tracing that service's own requests. You get the richer application spans from the language agent, while eBPF keeps tracing the services around it, all on one connected trace.

## Instrument everything (advanced)

The default and recommended model is to instrument per service. For automated rollouts, the agent also supports an autonomous mode that instruments every eligible service without per-service toggles. This is an advanced option; see [Advanced configuration](../../advanced-configuration/).
