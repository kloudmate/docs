Argo CD and Flux keep your cluster matched to what's in git. The KloudMate agent detects the workloads they manage and doesn't change them, so you can't turn on **SDK** tracing for those workloads from KloudMate. You can still trace them in other ways. Start with eBPF mode and work down the list.

| Approach | Pods restart | Repo change | Argo CD or Flux change |
|---|---|---|---|
| [eBPF mode](#turn-on-ebpf-mode) | No | None | None |
| [Namespace annotation](#annotate-the-namespace) | Once | Usually none | None |
| [Committed annotation](#commit-the-annotation) | Once | One line per workload | None |
| [Agent patching](#allow-the-agent-to-patch-these-workloads) | Once | None | Two settings |
| [Policy engine](#use-your-own-policy-engine) | Once | A policy manifest | None |

## Why the agent doesn't patch these workloads

To turn on SDK tracing, the agent adds an OpenTelemetry Operator annotation to the workload's pod template. Your controller removes anything that didn't come from git, and the agent would add the annotation again on the next check-in. Each change to the pod template restarts the pods, so they would restart once a minute, and nothing would show up as an error.

The agent checks the markers that each controller adds to a workload. Argo CD's tracking annotation, an Argo-prefixed instance label, and the labels that Flux's kustomize-controller and helm-controller add all identify the controller directly, so the agent trusts them on any cluster.

Argo CD with label-based resource tracking is the exception. It marks a workload only with the `app.kubernetes.io/instance` label, and plain Helm charts set the same label. So the agent trusts this label only on a cluster where Argo CD itself runs. On such a cluster, a workload that you installed with Helm and never put under Argo CD also shows as managed by Argo CD. Any of the options below still instruments it.

:::note[When Argo CD runs outside the cluster]
A central Argo CD that manages this cluster from somewhere else installs nothing in it, so the agent can't see Argo CD. With annotation tracking, detection still works, because each resource carries the tracking annotation. With label tracking, the agent finds no marker, so it keeps patching those workloads and restarting their pods.

Annotation tracking is the default from Argo CD 3.0. On an older version, set `application.resourceTrackingMethod` to `annotation+label` first, then to `annotation`. You can also use any of the options below, because none of them depend on detection.
:::

## Check whether a workload is externally managed

Go to **Settings → Agents & Pipelines**, open the cluster agent's actions menu (⋮), and select **Configure**. On the **APM** tab, the **Application Performance Monitoring** card shows **Managed by Argo CD** or **Managed by Flux** on a managed workload once you set it to **eBPF** or **SDK** and the agent checks in. A workload left at **Off** doesn't carry the label, but a banner at the top of the card tells you when Argo CD runs in the cluster. Other workloads work as usual, even on a cluster that runs Argo CD.

## Turn on eBPF mode

Set the workload to **eBPF** in **Application Performance Monitoring** and click **Apply**. The change takes effect on the next agent check-in. The agent doesn't change your cluster objects or your manifests, and no pods restart, because eBPF attaches to processes that are already running.

You get request rate, errors, duration, and trace spans. You don't get the in-process detail that an SDK adds, such as spans for database queries, framework internals, and outbound HTTP calls. For Go, Ruby, and PHP, eBPF is the only option on Kubernetes, whatever manages the workload, because KloudMate doesn't inject an SDK for those runtimes there. Those workloads aren't traced until you select eBPF for each one.

## Annotate the namespace

The OpenTelemetry Operator reads the inject annotation from the Namespace object as well as from a pod template, so one annotation covers every pod in the namespace:

```bash
kubectl annotate namespace payments \
  instrumentation.opentelemetry.io/inject-java=km-agent/km-agent-instrumentation-crd
```

Swap `inject-java` for the runtime you need: `inject-nodejs`, `inject-python`, or `inject-dotnet`. In a manifest, the same annotation looks like this:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments
  annotations:
    instrumentation.opentelemetry.io/inject-java: km-agent/km-agent-instrumentation-crd
```

Under Argo CD, the `CreateNamespace=true` sync option often creates the namespace, instead of a manifest in the app repo. If yours is created that way, the Namespace object isn't part of any Application's desired state, so annotating it doesn't count as drift and nothing reverts it.

The annotation doesn't change running pods. New pods get the injection, so delete the running ones or wait for the next deploy. Deleting pods doesn't create drift, because your controller manages the Deployment, not the pods it creates.

Keep these limits in mind:

- **Every pod in the namespace gets injected**, including short-lived jobs.
- **One runtime per namespace.** The annotation sets a single language. If a namespace holds a Java service and a Python service, this covers only one of them.
- **.NET runtime options come from the pod only.** If a .NET workload needs one, put it on that workload's pod template.
- **The workloads show Off in Application Performance Monitoring.** The agent didn't add the annotation, so it doesn't track these workloads, but their traces still reach KloudMate.

## Commit the annotation

Add the annotation to the workload's pod template in your repo, where it goes through review like any other change:

```yaml
spec:
  template:
    metadata:
      annotations:
        instrumentation.opentelemetry.io/inject-java: km-agent/km-agent-instrumentation-crd
```

Your controller applies it on the next sync, and the pods restart once. Argo CD and Flux need no extra configuration, because the annotation is part of the desired state.

Also set that workload to **SDK** in **Application Performance Monitoring**. The agent still doesn't change the workload. The setting keeps the workload tracked in KloudMate, and after your controller syncs the annotation, the workload shows as **Instrumented**.

## Allow the agent to patch these workloads

If you'd rather keep the per-workload toggle in KloudMate, set up Argo CD to accept the agent's annotation, then turn the agent's patching back on. You need both of the Argo CD settings below.

First, ignore the inject annotations in the `argocd-cm` ConfigMap:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: argocd
data:
  resource.customizations.ignoreDifferences.apps_Deployment: |
    jsonPointers:
      - /spec/template/metadata/annotations/instrumentation.opentelemetry.io~1inject-java
      - /spec/template/metadata/annotations/instrumentation.opentelemetry.io~1inject-nodejs
      - /spec/template/metadata/annotations/instrumentation.opentelemetry.io~1inject-python
      - /spec/template/metadata/annotations/instrumentation.opentelemetry.io~1inject-dotnet
```

Inside a JSON pointer, `~1` stands for the `/` in the annotation key. Keep only the runtimes you instrument.

Second, add the sync option to every Application whose workloads you instrument:

```yaml
spec:
  syncPolicy:
    syncOptions:
      - RespectIgnoreDifferences=true
```

:::caution
`ignoreDifferences` on its own only changes what Argo CD reports as drift. Self-heal still reverts the annotation, so the pods keep restarting while the Argo CD UI shows the Application as synced. `RespectIgnoreDifferences=true` keeps the field out of the sync itself.
:::

With both settings in place, turn the agent's patching back on with the `patchExternallyManagedWorkloads` Helm value:

```bash
helm upgrade kloudmate-release kloudmate/km-kube-agent \
  --namespace km-agent --reuse-values \
  --set patchExternallyManagedWorkloads=true
```

If Argo CD installs the agent, as in [Install the agent on a GitOps cluster](#install-the-agent-on-a-gitops-cluster), set the value in the agent's Application instead. Argo CD reverts a `helm upgrade` to the values in the Application:

```yaml
spec:
  source:
    helm:
      valuesObject:
        patchExternallyManagedWorkloads: true
```

This value applies to the whole cluster. If an Application doesn't have the settings above, Argo CD reverts the annotation and the Application's pods keep restarting. With the value on, workloads that Argo CD manages no longer show **Managed by Argo CD** in **Application Performance Monitoring**. They show their usual instrumentation status instead.

These steps are for Argo CD. On Flux, exclude the same annotations from drift correction before you turn on `patchExternallyManagedWorkloads`, or Flux reverts the agent's changes.

## Use your own policy engine

If you already run Kyverno, have it add the annotation to pods when they're created:

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: kloudmate-instrumentation
spec:
  rules:
    - name: annotate-java-pods
      match:
        any:
          - resources:
              kinds:
                - Pod
              namespaces:
                - payments
      mutate:
        patchStrategicMerge:
          metadata:
            annotations:
              instrumentation.opentelemetry.io/inject-java: km-agent/km-agent-instrumentation-crd
```

Argo CD and Flux compare Deployments, not the pods those Deployments create, so a policy that annotates pods never shows up as drift. The OpenTelemetry documentation suggests the same pattern. As with the namespace annotation, running pods get the annotation when they're recreated, and the workloads show **Off** in **Application Performance Monitoring** while their traces still reach KloudMate.

The OpenTelemetry Operator injects the SDK from its own admission webhook, which Kubernetes calls once per pod. That webhook has to run after Kyverno's, or it never sees the annotation. km-kube-agent charts released after 2.5.1 order the webhooks this way. On an older chart, set the order yourself:

```bash
helm upgrade kloudmate-release kloudmate/km-kube-agent \
  --namespace km-agent --reuse-values \
  --set opentelemetry-operator.admissionWebhooks.namePrefix=zz
```

Without it, pods get the annotation but no SDK, and nothing reports an error.

## Install the agent on a GitOps cluster

Install the agent with Helm, as shown in the [Kubernetes installation guide](../../installation/kubernetes-agent/).

To manage the agent through Argo CD instead, set these on its Application:

- **`ignoreDifferences` on the agent's own ConfigMaps, with `RespectIgnoreDifferences=true`.** The agent writes each collector's live configuration into the `/data/agent-daemonset.yaml` and `/data/agent-deployment.yaml` keys of `km-agent-configmap-daemonset` and `km-agent-configmap-deployment`. Argo CD renders the chart without reading the cluster, so it sees that configuration as drift. `ignoreDifferences` stops Argo CD from reporting it, and `RespectIgnoreDifferences=true` stops a sync from writing the chart's configuration over it. Without the sync option, any change to the Application, such as a new chart version or a Helm value, resets the collectors and drops the cluster's eBPF and SDK selections until the next **Apply** in KloudMate.
- **The destination namespace set to `km-agent`.** The chart always creates the Instrumentation resource in `km-agent`, and the inject annotation points to it as `km-agent/km-agent-instrumentation-crd`.
- **`SkipDryRunOnMissingResource=true`** in the sync options. On the first sync, Argo CD applies the Instrumentation resource in the same wave that installs the OpenTelemetry Operator's CRDs, and the dry run fails without this option.

```yaml
spec:
  destination:
    namespace: km-agent
  syncPolicy:
    syncOptions:
      - SkipDryRunOnMissingResource=true
      - RespectIgnoreDifferences=true
  ignoreDifferences:
    - group: ""
      kind: ConfigMap
      name: km-agent-configmap-daemonset
      jsonPointers:
        - /data/agent-daemonset.yaml
    - group: ""
      kind: ConfigMap
      name: km-agent-configmap-deployment
      jsonPointers:
        - /data/agent-deployment.yaml
```

## Upgrade the agent automatically

One-click upgrade from KloudMate doesn't work for an agent that Argo CD manages, because Argo CD reverts the agent to the chart version in its Application. Let Argo CD upgrade the agent instead: set the chart version to a range and turn on automated sync.

With `targetRevision: ">=2.0.0"`, Argo CD installs the newest chart version that is 2.0.0 or later, including future major versions such as 3.0.0, so you don't need to change the Application again. A range such as `2.*` stops at the last 2.x release. To review major versions before they roll out, use `">=2.0.0 <3.0.0"` and raise the upper bound yourself.

### Install a new agent with automatic upgrades

Create a Secret with your API key in the `km-agent` namespace:

```bash
kubectl create namespace km-agent
kubectl -n km-agent create secret generic km-agent-api-key --from-literal=API_KEY=<your-api-key>
```

Then create the Application. Set `clusterName` to the name you want to see in KloudMate, and `monitoredNamespaces` to the namespaces to monitor:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: km-agent
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://charts.kloudmate.com
    chart: km-kube-agent
    targetRevision: ">=2.0.0"
    helm:
      releaseName: kloudmate-release
      valuesObject:
        existingSecretName: km-agent-api-key
        clusterName: <cluster-name>
        monitoredNamespaces: "default, prod"
        featuresEnabled:
          logs: true
          apm: true
  destination:
    server: https://kubernetes.default.svc
    namespace: km-agent
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
      - SkipDryRunOnMissingResource=true
      - RespectIgnoreDifferences=true
  ignoreDifferences:
    - group: ""
      kind: ConfigMap
      name: km-agent-configmap-daemonset
      jsonPointers:
        - /data/agent-daemonset.yaml
    - group: ""
      kind: ConfigMap
      name: km-agent-configmap-deployment
      jsonPointers:
        - /data/agent-deployment.yaml
```

### Turn on automatic upgrades for an existing agent

If Argo CD already runs the agent, add these settings to its Application. Keep the existing `repoURL`, `chart`, and Helm values:

```yaml
spec:
  source:
    targetRevision: ">=2.0.0"
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - SkipDryRunOnMissingResource=true
      - RespectIgnoreDifferences=true
  ignoreDifferences:
    - group: ""
      kind: ConfigMap
      name: km-agent-configmap-daemonset
      jsonPointers:
        - /data/agent-daemonset.yaml
    - group: ""
      kind: ConfigMap
      name: km-agent-configmap-deployment
      jsonPointers:
        - /data/agent-deployment.yaml
```

If you installed the agent with `helm install` and Argo CD doesn't manage it, you don't need any of this. Upgrade it from KloudMate, as described in [Upgrade the agent](../../upgrade/).

### When upgrades happen

Argo CD installs a new release the next time it refreshes the chart repository. To install it right away, run a hard refresh on the Application. The `ignoreDifferences` entries and sync options keep the cluster's eBPF and SDK selections through each upgrade, as explained in [Install the agent on a GitOps cluster](#install-the-agent-on-a-gitops-cluster).

If an ApplicationSet or a parent Application generates the agent's Application, make these changes in its source in git. Otherwise the parent overwrites a change you make in the Argo CD UI.

With Flux, set the same range in the HelmRelease's `spec.chart.spec.version`.
