On a Linux host, how the agent attaches tracing to a service depends on the language **and** on how the service is run. A systemd unit, a PM2-managed app, and a bare process each expose a different hook, so the agent picks the right one for each. This page is the reference for what is supported where, and what to watch out for.

For the per-service flow, restart consent, and rollback that apply to every path, see the [Application APM overview](../overview/).

## Support matrix

| Runtime | systemd service | PM2 app | Bare / other process |
|---|---|---|---|
| Java | Startup drop-in, then restart | Runtime attach, no restart | Runtime attach, no restart |
| Node.js | Startup drop-in, then restart | Restart with updated environment | Not automatic; run under systemd or PM2 |
| Python | Startup drop-in, then restart | Restart with updated environment | Not automatic; run under systemd or PM2 |
| .NET | Startup drop-in, then restart | Run under systemd | Run under systemd |
| PHP | `php.ini` scan directory, graceful reload | `php.ini` scan directory, graceful reload | `php.ini` scan directory, graceful reload |
| Go | eBPF monitoring, no injection | eBPF monitoring, no injection | eBPF monitoring, no injection |

Every path exports to the agent's local collector, so an instrumented service shares one trace with the [eBPF monitoring](../../ebpf-observability/) around it.

## systemd services

This is the primary path on Linux. When you instrument a systemd service, the agent writes a startup drop-in for that unit and, with your consent, restarts it so the change takes effect:

- **Java** loads the OpenTelemetry Java agent through `JAVA_TOOL_OPTIONS`.
- **Node.js** loads the instrumentation through `NODE_OPTIONS`.
- **Python** loads it through `PYTHONPATH`.
- **.NET** loads the CLR profiler through the `CORECLR_*` and `DOTNET_STARTUP_HOOKS` variables.

Because the restart lets the agent set configuration up front, a systemd service gets a stable, forced `service.name` (the name you see in the Discovered Services list), sampling, and the correct OTLP endpoint. Turning instrumentation off removes the drop-in and restarts the service, leaving it as it was. Applying the same choice twice does nothing, so it is safe to re-run.

## PM2 apps

PM2 apps have no systemd unit, so they get a different, restart-based path. The agent instruments **Node.js and Python** apps running under PM2 by restarting each selected app with the tracing environment applied (`pm2 restart <app> --update-env`). Each app keeps its own PM2 process name as its `service.name`, so several apps under one PM2 daemon stay distinct.

The agent covers every user's PM2 daemon on the host, not just root's. If an injected app fails to come back online, the agent withdraws the change and restarts the app, so a bad injection never leaves your app down.

Java under PM2 uses the runtime-attach path below instead. .NET under PM2 is uncommon and is not covered automatically; run a .NET service under systemd to instrument it.

## Java without systemd (runtime attach)

A JVM that is not a systemd service, whether it is a bare `java -jar` process, PM2-managed, or started by a script, can still be instrumented. The agent attaches the OpenTelemetry Java agent to the **running JVM** with no restart and no supervisor required. This is validated against real frameworks, including Spring Boot and Tomcat.

Runtime attach detects `service.name` automatically, in this order:

1. The jar name for a `java -jar app.jar` launch (so `app.jar` reports as `app`).
2. `spring.application.name`, when the app sets it.
3. Otherwise `unknown_service:java`.

Two things follow from attaching to a live JVM rather than restarting it:

- **You cannot force a specific `service.name`** on this path. If you need a fixed name, set `spring.application.name` in the app, or run it as a systemd service.
- **Attach is one-way.** An agent loaded at runtime stays until the JVM restarts, so turning instrumentation off does not remove it from an already-running JVM. It takes effect on the next restart.

## Bare Node.js and Python

Node.js and Python only have a supervised attach path. A bare, unsupervised Node.js or Python process, one with no systemd unit and not under PM2, has no per-process hook the agent can use. To instrument it, run it under **systemd or PM2** first. The Discovered Services list reports these as not automatically instrumentable and points you to this prerequisite.

## PHP

PHP is instrumented through the PHP configuration, not a process restart. The agent adds a file to the PHP scan directory for the target's own PHP build, then reloads the SAPI gracefully (a php-fpm or Apache reload) so no connections drop. It works on **PHP 8** with the native OpenTelemetry extension, and falls back to a tracer that also covers **PHP 7**. See [PHP instrumentation](../php/).

## Go

Go is not injected. It is covered by [eBPF monitoring](../go-ebpf/), which gives Go services RED metrics, the service map, and spans from the kernel with no attach step. This is the same on systemd, PM2, and bare processes.

## How discovered services are named and filtered

The agent keeps the Discovered Services list to real application workloads:

- **Infrastructure and the agent's own processes are excluded.** The agent never lists or instruments itself, cloud-provider guest agents (such as the AWS SSM agent, the Google guest agent, or the Azure agent), or container runtimes (such as `containerd`, `dockerd`, and `kubelet`). Left in, these would clutter the list and could be traced as if they were your services.
- **A bare JVM is listed by its jar name.** A `java -jar app.jar` process shows as `app`, matching the `service.name` its traces carry, rather than the generic `java`.

For the full discovery model, see [Discovery](../../concepts/discovery/).

## Limitations

Keep these in mind, especially on the runtime-attach path:

- **Java runtime attach does not instrument the built-in `com.sun.net.httpserver`.** The JDK's own lightweight HTTP server registers its handler before the agent attaches, and that handler cannot be re-hooked afterward. Standard frameworks such as Spring Boot and Tomcat are fully instrumented; only apps serving directly from the JDK's built-in server are affected.
- **JDK 21 and newer print a dynamic-agent-loading warning.** Runtime attach triggers the JVM's `A future release of the JVM may disallow dynamic loading of agents by default` warning ([JEP 451](https://openjdk.org/jeps/451)). It is harmless today. A future JVM may require you to start the app with `-XX:+EnableDynamicAgentLoading` for runtime attach to keep working.
- **Bare Node.js and Python need a supervisor.** Without systemd or PM2, there is no automatic attach path for these runtimes.
- **Go is eBPF-only.** There is no code injection for Go; its coverage comes from eBPF monitoring.
